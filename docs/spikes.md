# Spike results (design §16)

All spikes ran on Thu 5 Nov 2026 in the PayPal sandbox. The merchant is an **India (IN) business** sandbox account and the buyer is a **US personal** sandbox account. PayPal India has handled only cross-border payments since 1 April 2021, so this pairing matches how Indian sellers actually use PayPal.

| # | What we tried | Result | Consequence |
|---|---|---|---|
| S1 | OAuth token, then `GET /v1/customer/disputes` | **Pass.** 200, 0 disputes. | none |
| S2 | Card-funded order with a sandbox Visa | **Fail.** 422 `PAYEE_NOT_ENABLED_FOR_CARD_PROCESSING`. India merchants can't take cards. | Card paths are off (`SHOPPER_TEST_CARD=0`). Orders are paid with the buyer's saved PayPal wallet (S5) or through the storefront. |
| S2 | `/v2/checkout/orders/{id}/track` with carrier `INDIA_POST`, then GET the order | **Pass.** 201. The tracker `<capture>-EE…IN` (SHIPPED) shows on the order straight away, and `custom_id` is kept. | `pp.order.tracking` works, and `rehydrate` can rebuild shipments. |
| S3 | `process-chargeback` on saved-wallet captures with codes 10.4/VISA, 13.1/VISA, 4853/MASTERCARD and 1330/VISA | **Fail.** HTTP 500 on all four, and no dispute was created. Chargebacks need a card-funded payment, which this merchant can't have. | `CHARGEBACK_ENABLED=0`. All 12 bench cases are synthetic snapshots shaped on these responses. The hosted "New sandbox dispute" button is off. |
| S5 | Vault v3: setup token, then buyer approval (done once by hand), then payment token, then an order with `payment_source.paypal.vault_id` | **Pass.** The order was COMPLETED instantly with no buyer login. The capture's `seller_protection` is ELIGIBLE and the payer country is US. | `SHOPPER_VAULT_TOKEN` is set. The seed CLI (`order --pay vault`) and the shopping agent pay automatically. |
| S6 | `paypal-agent-toolkit` 1.1.0 for dispute reads | **Not usable.** The Python toolkit has no dispute tools, and `get_order_details` returns a summary, not the order. | Reads go over REST. The remote PayPal MCP server (`mcp.sandbox.paypal.com`), which lists `get_dispute` and `list_disputes`, is still to try. |
| S7b | Groq `openai/gpt-oss-20b`, strict `json_schema` with `Verdict` and `BuyerTurn` | **Pass.** Valid JSON in 5.7 s and 7.3 s, including the fallback from the local provider, which was down. | Groq works as the hosted primary or the fallback. |
| S4 | Buyer-opened INR case on the vault order (sandbox UI, 10 Nov), then `fetch_snapshot` | **Pass, but not the shape the design assumed.** `PP-R-IIX-10197974` showed up in the API after ~3.5 min as stage **CHARGEBACK**, channel **INTERNAL** (a PayPal claim, not a card chargeback), status **UNDER_REVIEW**. The only seller link was `provide-supporting-info`. The buyer's text is in `evidences[].notes` (`CREATE` / `SUBMITTED_BY_BUYER`), not `messages[]`. `disputed_transactions[0].seller_protection_eligible: true` (`EXPANDED_SELLER_PROTECTION`). Sandbox `require-evidence` returned 400 `ACTION_NOT_ALLOWED_IN_CURRENT_DISPUTE_STATE`. | Added a 5th seller action, `provide_supporting_info`. The card-chargeback coverage rule now requires channel EXTERNAL. New facts: `pp.dispute.channel`, `pp.dispute.protection`. |
| S1b | `provide-supporting-info` from the app (merchant approved run #6 in the UI) | **Pass.** HTTP 200, debug id `f5913653c8bff`. The dispute then shows `supporting_info` SUBMITTED_BY_SELLER with our notes, and PayPal opened new links: `adjudicate`, `require-evidence` and `accept-claim`. | A ruling (`adjudicate`) can end the demo. `provide-evidence`, `make-offer` and `send-message` still need a case that exposes them. |
| Model quota | Groq free tier, read from the headers | Each model allows 8k tokens/min and 1k requests/day, and quotas are per model. One desk hearing is about 23k tokens with gpt-oss (mostly hidden reasoning). | `reasoning_effort: low` for gpt-oss. Primary is gpt-oss-120b with gpt-oss-20b as fallback, and cooldowns are keyed per model. 429s are waited out (the body's "try again in Ns" first, at most 75 s total). Gemini 2.5 Flash's free quota ran out on the first bench trial, so the bench runs on local Qwen3-4B (S7) and Groq's daily quota stays free for the hosted demo. |
| D1 | Hosted `GET /api/whoami` on Render (12 Nov), plain and with forged `X-Forwarded-For`, `True-Client-IP` and `CF-Connecting-IP` headers | **`xff-last` is wrong on Render.** Its value is Render's internal proxy (`10.x`), so every visitor would share one rate-limit bucket. Cloudflare replaces `True-Client-IP`, rejects a forged `CF-Connecting-IP` (error 1000), and lets a forged leading `X-Forwarded-For` entry through. | `CLIENT_IP_HEADER=cf-connecting-ip` (set in `render.yaml`). `xff-first` would be spoofable. |
| S7 | Local Qwen3-4B (Q5_K_M) on llama.cpp `llama-server`, GPU, 8k context, strict `json_schema` | **Pass, after tuning.** About 14 s per call. Without length limits in the grammar, `BuyerTurn` looped until the call timed out; a 1536-token cap then truncated JSON. | Locally the grammar keeps `maxLength`/`maxItems`, thinking is off, `repeat_penalty` 1.1, `max_tokens` 3072. Over-long fields from object-mode models are truncated, not rejected. This is the bench model. |
